## 0. 一句话

读取单机游戏的**日志 + 存档**，让游戏角色变成一个能常驻桌面、**在该说话的时候才说话**的桌宠；
立绘按角色人设生成多风格多动作，退出游戏后带着刚才那局的记忆继续聊。

## 1. 需求 → 工程约束

| 需求原话 | 工程含义 |
|---|---|
| 「读取日志和**每一次的存档更新**」 | 需要一个**文件监视 + 结构 diff** 层，而不是每次重新解析一遍 |
| 「结合网上的角色介绍 + 用户的提示词」 | 角色卡**生成**链路（抓取 → 抽取 → 校验 → 落库），且必须可导入/可手改 |
| 「**完整的**项目，前端 / api 配置页 / 人物卡生成导入页」 | 明确是**桌面应用**（多窗口），不是网页 Demo |
| 「根据立绘绘制出**不同风格、不同动作**」 | 素材**生成**链路 + **动作清单契约**（角色卡声明要哪些动作） |
| 「打败 boss 存好档的**松懈时间**、或**角色死亡后**交流」 | ★ **时机引擎**：只在泄压点主动开口，其余时间闭嘴 |
| 「**这样的度** + 读取日志和存档的局限**刚刚好**」 | ★ 见 §3：局限不是缺陷，是设计资源 |
| 「退出游戏后带着**刚才游戏的记忆**继续聊」 | 跨会话记忆：写（带权重）→ 召回（按当前话题相关）→ 淘汰 |

## 2. 现实侦察：三种引擎到底给得出什么（★ 实测）

用户确定先支持 **RPG Maker / Unity 2D / Godot**。这不是靠猜格式 —— 本机 `%USERPROFILE%\AppData\LocalLow`
下有 **60+ 款 Unity 游戏**的真实存档与日志，`%APPDATA%\Godot\app_userdata` 下有 1 款真实的 Godot 游戏。
下面每一行都是实际打开文件看过的。

### 2.1 日志

| 引擎 | 路径 | 实测内容 | 能抽出什么 |
|---|---|---|---|
| Unity | `LocalLow\<公司>\<产品>\Player.log`（另有 `Player-prev.log`） | 空洞骑士 2,892B；丝之歌 **6,226,118B / 129,392 行**。**全是引擎噪声**：Mono 路径、GfxDevice、`Couldn't find a Game Manager` ×上万行 | ★ **会话边界**：开头 `Initialize engine version`、结尾 `Input System module state changed to: Shutdown`；`Steam logged in as <玩家名>`；`Loaded saved language code`。**游戏内事件几乎没有** |
| Godot | `%APPDATA%\Godot\app_userdata\<项目名>\logs\godot.log`（实测 31,677B） | 引擎噪声 + `USER ERROR: Node not found: "../../NPC_AoKawa" (relative to "/root/Home/...")` | ★ **节点路径泄漏语义**：`/root/Home`、`/root/Office` → 玩家**在哪个场景**；节点名 `NPC_AoKawa` / `Char_Himemiya` → **当前场景有哪些角色** |
| RPG Maker MV/MZ | **默认没有** | —— | 无日志通道，**只靠存档** |

> **官方文档佐证**：Unity Player 日志位置见 [Unity Manual: Log files](https://docs.unity3d.com/Manual/LogFiles.html)
> （Windows：`%USERPROFILE%\AppData\LocalLow\CompanyName\ProductName\Player.log`）；
> Godot `user://` 位置见 [Godot Docs: File paths](https://docs.godotengine.org/en/stable/tutorials/io/data_paths.html)
> （默认 `%APPDATA%\Godot\app_userdata\[project_name]`，启用自定义目录后为 `%APPDATA%\[project_name]`）。

**结论（重要）**：**日志不是游戏事件的可靠来源**。它可靠地给出「这局开始了 / 这局结束了 / 崩了」，
以及少数开发者恰好写进 `Debug.Log` 的东西。**任何"从日志里读到 Boss 名字"的设计都是不成立的**。

### 2.2 存档

| 引擎 / 样本 | 实测 | 判定 |
|---|---|---|
| Godot `.tres`（本机一款视觉小说，3,236B） | **纯文本、逐字段可读**：`slot_info_saved_day="2025-05-01"` `slot_info_saved_time="01:20:01"` `current_scene="Home"` `current_day=21` `triggered_stories=Array[String]([...43 条...])` `*_route=24` `item_*=true/false` | ★★★ **最佳情况**。`triggered_stories` 的**新增项 = 这局推进了什么**；`*_route` 数值 = 角色关系状态 |
| Godot `settings.ini`（671B） | INI / ConfigFile，`[Ending] MinaseA=false` 等 | ★★★ 纯文本，好 diff |
| Unity 明文 JSON（森林之子 `PlayerProfile.json`，467B） | `{"_settings":[{"Name":"Stats.CoreGameCompleted","BoolValue":true}, ...]}` | ★★★ **成就/进度布尔量**直接可读 |
| Unity **.NET BinaryFormatter**（空洞骑士 `user1.dat` 381KB；DDLC `save_persistent.sav`） | magic `00 01 00 00 00 ff ff ff ff 01` = `SerializationHeaderRecord` | ★☆☆ 需要二进制反序列化器，且内含 Unity 对象图 |
| Unity **高熵容器**（致命公司 `LCGeneralSaveData`；胡闹厨房 `Meta_SaveFile.save`） | magic 分别为 `18 d0 06 a2 …` / `b8 cd 33 be 5d b0 e9 b9`，高熵 | ✗ 加密或私有压缩，**解不开** |
| Unity **zip 存档**（森林之子 `SaveData.zip` 6,735B + 带时间戳的备份 zip） | 真 zip 容器 | ★★☆ 需 zip 读取（零依赖可做） |
| Noita（Unity，但自研格式） | `save00/{world,stats,persistent}/`，`mod_config.xml`、`mod_settings.bin`、`persistent/bones_new/item*.xml` | ★★☆ XML 可读，但世界存档巨大 |
| RPG Maker MV/MZ `.rpgsave`/`.rmmzsave` | **LZString 的 compressToBase64 输出，解出来就是 JSON** | ★★★ 且内含 `$gameSwitches`/`$gameVariables`/`$gameParty`（等级/道具）/`$gameMap` |

> **佐证**：`.rpgsave` 是 lz-string + base64 的说法见 [Gteditor99/rpgsave-decode](https://github.com/Gteditor99/rpgsave-decode)
> 的 `main.go` 头部注释与 `lzstring.DecompressFromBase64` 调用。
> Unity PlayerPrefs 在 Windows 落 `HKEY_CURRENT_USER\Software\<公司>\<产品>`
> （见 [Unity ScriptReference: PlayerPrefs](https://docs.unity3d.com/ScriptReference/PlayerPrefs.html)；
> 编辑器内是 `HKCU\Software\Unity\UnityEditor\<公司>\<产品>`，且**键名被哈希**）。

### 2.3 侦察得出的三条硬结论

1. **Unity 的日志不可指望，存档才是主信号**；Godot 两边都有货；RPG Maker 只有存档。
2. **存档格式是一个谱系**，从「纯文本 JSON」到「加密二进制」连续分布，**不可能靠一个解析器通吃**。
3. 因此**必须能降级** —— 见 §3。

## 3. ★ 核心洞见：局限是设计资源，不是缺陷

用户说「读取日志和存档的局限**应该是刚刚好的**」。这个判断是对的，而且可以推得更远：

> **桌宠看不见细节，所以它只能问。而"问"就是交互本身。**

如果它能读到一切，它就会变成**旁白**——复述玩家刚做过的事，既无聊又冒犯人。
正因为它只看得见「存档在 01:47 被写入了，而且比上次多了 3 条剧情 flag」，
它只能这样开口：

> 「你刚存档了 —— 打完了？还是又没了。」

而这句话恰恰是玩家想听的。**信息缺口 = 对话的燃料。**

由此得到两条贯穿全局的设计原则：

- **P1｜只报事实，其余用问的。** 确定性代码给出的事实（"存档变了""多了 3 条进度""游戏退了"）可以直说；
  一切细节必须用**疑问句**，不能编。这条同时解决了「模型不许发明剧情」的老问题。
- **P2｜宁可只说"你存档了"。** 内容解析（diff）是**锦上添花**，不是主线。
  **即使一个游戏完全解不开（见 §2.2 加密存档），仅凭"存档文件被写入"这个事实，时机引擎依然完整可用。**
  这条决定了实现顺序：**时机引擎先于解析器**。

## 4. 分层

```
┌─ Electron 外壳 ────────────────────────────────────────────┐
│  桌宠窗（透明/置顶/穿透点击）  设置窗（API 配置 / 角色卡 / 素材）  │
└──────────────┬─────────────────────────────────────────────┘
               │ IPC（preload + contextBridge）
┌──────────────┴─────────────────────────────────────────────┐
│  app/            主进程：编排、窗口、IPC、持久化                │
├────────────────────────────────────────────────────────────┤
│  presence/       ★ 时机引擎：什么时候可以开口（§5）              │
│  dialogue/       表达层：provider 可插拔（模板 → LLM）           │
│  card/           角色卡生成 / 导入 / 校验                       │
│  art/            素材层：立绘 → 多动作（provider + 程序化兜底）    │
├────────────────────────────────────────────────────────────┤
│  core/           纯逻辑，零依赖，**全部可单测**                  │
│    events  diff  decode  persona  presence  memory  card      │
├────────────────────────────────────────────────────────────┤
│  gameio/         引擎 adapter（可插拔）                        │
│    unity/  godot/  rpgmaker/        log 通道 + save 通道       │
└────────────────────────────────────────────────────────────┘
```

**依赖方向严格单向**：`gameio` 与 `core` 不认识 Electron，也不认识任何具体游戏。
adapter 的唯一职责是「翻译成统一事件形状」（`core/events.mjs` 已定义）。

## 5. 时机引擎 —— 「度」到底怎么落地

这是本项目**最该被量化**的部分。做法照搬上个项目的经验：
把「感觉刚刚好」拆成**可测的规则 + 可观测的指标**。

### 5.1 触发源与判定

| 触发源 | 实测可得 | 泄压点？ |
|---|---|---|
| 存档文件被写入 | 所有引擎（文件系统层面） | ★ 是。存档 = 玩家主动留 checkpoint，天然松弛 |
| 存档 diff 有新进展 | 取决于能否解码 | 是，且**信息量更大**（知道"多了 3 条剧情"） |
| 游戏进程退出 | 进程表 | 是（转为"离开后的余韵"对话） |
| 日志出现死亡/失败行 | 仅当开发者恰好打了 | 是 |
| 玩家键鼠空闲变长 | 系统 API，**总是可得** | ★ 是。见下面的「专不专心」问题 |

**★ 「玩家专不专心」不能靠日志活动判断（实测结论）。**
Unity 的 `Player.log` 在进行游戏时几乎不产出内容（实测单个文件 6MB 全是引擎噪声），
所以"存档之后有没有新日志行"**根本区分不出**「打完 boss 放下手柄」和「接着打下一段」。
真正的判据是**系统空闲时长**（Electron 的 `powerMonitor.getSystemIdleTime()`）。
因此静默判定拆成两个独立信号：

| 信号 | 来源 | 作用 |
|---|---|---|
| `activity` | 文件/日志新动静 | 合并存档写入的突发；对 Godot / RPG Maker 这类日志确实有内容的引擎也有用 |
| `relaxed` | 系统空闲秒数 ≥ 阈值 | **Unity 场景下唯一可靠的「已松懈」信号** |

### 5.2 三层闸门（缺一不可）

1. **去抖（debounce）**：游戏自动存档可能每 30s 一次，且一次存档常写多个文件。
   → 合并成一次"存档事件"，并做**显著性过滤**：diff 无实质变化 ⇒ 不算事件。
2. **静默判定（settle）**：存档写入后**再等 N 秒**。若期间又有写入/新日志行 ⇒ 玩家还在玩 ⇒ 这次不算。
3. **节流 + 预算**：同类触发冷却、每小时主动发言上限。

```
允许主动发言  ⇔  不在"专注中"（空闲够久）  ∧  在泄压点  ∧  冷却已过  ∧  本小时预算未用完
冷却时长       ←  主动档位  ×  caution（被忽略越多越谨慎） ×  affinity（生疏时更克制）
每小时预算     ←  主动档位 ÷ caution          （刻意**不**被 affinity 缩放，见下）
```

> **预算为什么不随亲密度缩放**：`budgetPerHour` 是给用户看的硬承诺（"每小时最多说几次"），
> 让它随亲密度悄悄减半会让这个设置失去可预期性。「越生疏越克制」体现在**冷却时长**上。

**★ 「到了静默窗口但玩家还在玩」必须继续等，不能丢弃。**
这是实现中最容易做错的一处：若在那里丢掉待发言，就等于**要求玩家必须在存档后 20 秒内停手**，
而用户描述的是「存档后接着打一会儿、再放下手柄」。
所以待发言会**一直等到玩家松懈**，只受一个 `pendingTtlMs`（保守档 5 分钟）兜底 ——
免得拿十分钟前的存档去搭话。测试里 `★ 存档后接着打两分钟再放下手柄 → 仍然开口` 钉住了这条。

### 5.3 自适应：被忽略就变安静

主动发言后若玩家没有回应，**下调**主动程度；被回应则上调。
这让「度」不需要人肉调参，并且**是可测的**：同一段事件流跑一遍，能数出它说了几句话。

### 5.4 可观测指标（用来证明"度"是对的，而不是感觉对）

由 `core/presence.mjs` 的 `summarize()` 产出，可对同一份事件流离线回归：

| 指标 | 含义 | 期望 |
|---|---|---|
| `speaksPerHour` | 每小时主动发言次数 | 有上界，且不随游戏时长线性增长 |
| `triggerLatencyMs` | 从触发出现到开口的延迟 | 反映"等玩家松懈"的时长，不是 0 |
| `usedTriggerRate` | 被使用的触发比例 | **不是 100%**（100% 说明太吵） |
| `ignoredStreak` / `caution` | 连续被忽略次数 / 谨慎度 | 被忽略后上升，被回应后回落 |
| `silenceDuringPlay` | 玩家专注游戏期间的发言次数 | **必须为 0**（不是假设，是实测计数） |
| `waitedForFocus` | 因玩家专心而推迟的次数 | 不是失败，是"在等" |
| `droppedExpired` | 等到过期都没等到松懈 | 过高说明阈值太严 |

### 5.5 调整空间必须被「实际读得到什么」框住

用户要求「留给用户调整的空间」，同时又说「如果真的读不出信息，还是只给保守选项」——
这两句合起来是一个**硬规则**，不是偏好：

> 把档位调高却读不到新东西，只会逼桌宠编内容，直接违反「只报事实」。
> 所以 **adapter 声明的可读事件类型决定档位上限**。

- `RELIABLE_KINDS` = `save` / `exit` / `manual`：只靠文件系统与进程表就能拿到，**不需要游戏配合**
- `ADAPTER_KINDS` = `death` / `progress` / `combat` / `item` / `area`：**必须由 adapter 证明它读得出来**

一个只读得到前者的 adapter，无论用户怎么调，`resolvePolicy()` 都会封顶在保守档，
并给出理由（而不是默默改掉用户的设置）。

## 6. 解码链（必须可降级）

`core/decode.mjs` 按顺序尝试，**任一步失败就继续**，最终一定返回一个结果：

```
读文件 → JSON? → gzip/zlib? → LZString(base64)? → Godot .tres / .ini 文本?
       → zip 容器? → .NET BinaryFormatter? → ★ 放弃内容，退回 hash-only
```

**`hash-only` 是一等公民，不是错误分支**（§3 原则 P2）：它照样产出「存档已更新」事件。

## 7. 素材层：立绘 → 多风格多动作（已实现，见 `art/`）

用户要的是「不止傻站着，长时间不理人会做出无聊的动作」，并且
「根据角色的官方人设生成不同的动作，比如偏活泼一些的」。

**动作**——清单由**角色属性**推出，不是写死一套：
- `idle` / `idleBored` / `talk` 对所有卡必需（`idleBored` 尤其 —— 「长时间不理人」是用户点名的场景，
  不能由气质决定要不要），气质再追加：`lively` → greeting + happy，`calm` → happy，`cool` → worried
- **缺动作是可检出的**（`checkManifest` 查三类静默错误：缺 / 多余 / 帧数与词汇表不符）

**风格**——`card.animation.style` 有三档（`soft` / `pixel` / `line`），都是纯图像运算。
每种风格都有**方向性可验证**的性质，测试断言的就是这些方向而不是"输出不一样"：

| 风格 | 性质（实测） |
|---|---|
| `soft` | 模糊造出中间色（颜色数 4→32）、高频最低 |
| `pixel` | **保留调色板**（颜色数不增）、方块化 |
| `line` | 边缘占比与高频都是三者最高（只剩线） |

★ **管线顺序：风格化 → 动作，且比较基准是"风格化之后的立绘"。**
反过来的话线稿风会因"跟原图差太远"被判成跑形 —— 那是把**风格差异误判成跑形**。
（对照：生成式 provider 的基准应当是**原图**，因为「别跑形」的本意正是"别画得不像原本的角色"。
 两者的区别由 provider 的 `derivesFromSource` 显式表达。）

**兜底**——程序化 provider 是默认档，它**连立绘都能现画**（`synthStandingArt`），
所以"零输入"也跑得通。但它只做几何变换（位移 / 旋转 / 亮度）+ 风格化，
**不可能画出原图没有的姿势** —— 这一点写在它文件头，不假装能替代文生图。

**两条质量闸门**（本层最实在的部分）：
1. **动作间差异下限** —— 防止"六个动作其实是同一张图"（用户抱怨的"傻站着"）
2. **与立绘相似度下限** —— 防止"每个动作一张新图，角色跑形了"

两者都靠像素：`art/image.mjs` 有一套**零依赖的 PNG 编解码 + 感知哈希**。
没有它，这两条就只能停留在口头上。阈值也不是拍脑袋：
`node tools/art-check.mjs --measure` 打印实测值（动作间差 0.032、距基准 11），阈值取 0.01 / 24。

> 两个实测教训，都写进了 §5 的坑表：
> ① 判断"两个动作是不是同一个"要**特征帧**（离基准最远的那一帧），不能比起手帧 ——
>    桌宠从静止站姿起手是自然的，拿首帧比会把"共享起手姿势"误判成"偷懒"。
> ② 判断"是不是同一张图"的哈希位数不能太粗：8×8（64 位）下 1~3 像素的位移分不出来，
>    `idle` 与 `talk` 会算出同一个哈希 —— 要用 16×16（256 位）。

## 8. 技术栈（已定）

| 层 | 选型 | 理由 |
|---|---|---|
| 外壳 | **Electron** | 透明/置顶/穿透点击最成熟；Node 在主进程可同时管文件监视与图像 API。且 `powerMonitor.getSystemIdleTime()` **直接给出系统空闲秒数**，正好是"长时间不理人"要的信号（**推断**：待实测确认） |
| 前端 | **React + TypeScript + Vite** | 与上个项目一致，复用经验 |
| 主进程运行时 | **Node 24 内置能力** | `node:sqlite`（记忆/事件历史）、`node:test`（测试），**零依赖** |
| 文件监视 | `fs.watch` + 自写去抖 | 不引 chokidar |
| 进程探测 | `tasklist` / WMI | 判断"游戏是否在运行" |
| LLM | provider 抽象（OpenAI 兼容 / Anthropic / Gemini） | 配置页可切；**没配也能跑**（模板 provider） |
| 图像 | provider 抽象 + 程序化兜底 | 见 §7 |
| 编码 | 全程 UTF-8；PowerShell 脚本带 BOM | 上个项目踩过：PS 5.1 按 ANSI 读 `.ps1`，中文必乱 |

## 10. 已知风险与明确不做

**风险**
- Unity 加密存档（实测已有样本）→ 靠 §3 P2 的 `hash-only` 降级兜住。
- Unity `Player.log` 动辄几百 MB（实测 6.2MB~4.7MB 单个文件）→ 必须**尾读**，不能整文件读入。
- 游戏日志被 Steam 云同步目录搅动 → 需过滤 `steam_autocloud.vdf` 之类的噪声文件。

**不做**
- 不做**在线游戏**（读不到本地存档，且涉反外挂）。Arknights 那种属于上个项目。
- 不做**内存读取 / 注入 / 反编译**——只读文件系统上游戏自己写出的东西。
- 不承诺「读懂所有游戏」——承诺的是**能降级**且**降级后依然有用**。
