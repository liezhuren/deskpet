# 单机游戏角色陪伴桌宠 Agent

读取单机游戏的**日志与存档更新**，结合游戏设定资料与用户提示词，把游戏角色做成一个**常驻桌面**、
会挑时候开口的智能桌宠；立绘按角色人设生成多风格多动作；退出游戏后带着刚才那局的记忆继续聊。

> 个人复刻项目（同方向在公司做过一轮）。
> 目标不是"能聊天"，而是**「什么时候该说话」这件事可量化、可回归** —— 见 `docs/ARCHITECTURE.md` §3、§5。

---

## 它要解决的真问题

用户的原始要求是：「打败 boss 存好档的**松懈时间**和他交流，或者角色死亡后与用户交流，
**这样的度再加上读取日志和存档的局限应该是刚刚好的**。」

这个"度"是本项目的核心。而"读取日志和存档的局限"不是缺点 —— 桌宠只看得见"存档被写入了"，
看不见细节，所以它只能**问**；而"问"就是交互本身。**信息缺口是对话的燃料。**

由此得到两条设计原则：

1. **只报事实，其余用问的** —— 确定性代码给出的事实可以直说，细节必须用疑问句，不许编。
2. **内容解析是锦上添花，时机才是主线** —— 即使某个游戏的存档完全解不开，
   仅凭"存档文件被写入"这个事实，时机引擎依然完整可用。

## 「度」是怎么落地的（`core/presence.mjs`）

```
允许主动发言  ⇔  不在"专注中"（系统空闲够久）  ∧  在泄压点  ∧  冷却已过  ∧  本小时预算未用完
冷却时长       ←  主动档位 × caution（被忽略越多越谨慎）× affinity（生疏时更克制）
```

三个细节，都是踩过坑才定下来的：

- **玩家专不专心，不能靠日志活动判断。** Unity 的游戏日志在进行游戏时几乎不输出内容
  （实测单个文件 6MB 全是引擎噪声），所以"存档后有没有新日志行"区分不出
  「打完 boss 放下手柄」和「接着打下一段」。真正的判据是**系统空闲时长**。
- **存档后接着打一会儿再放下手柄，仍然是松懈时间。** 所以待发言会**一直等到玩家松懈**，
  而不是到点没等到就丢掉（丢掉等于要求玩家必须在存档后 20 秒内停手）。
  只用一个 5 分钟的过期时间兜底，免得拿十分钟前的存档去搭话。
- **发言和动作是两个通道。** 「长时间不理人做出无聊的动作」属于动作通道，几乎不打扰人，
  可以频繁；发言会打断人，必须稀缺。两者不共用预算。

「度对不对」不靠感觉，靠这几个指标（可对同一份事件流离线回归）：

| 指标 | 期望 |
|---|---|
| `speaksPerHour` | 有上界，不随游戏时长线性增长 |
| `usedTriggerRate` | **不是 100%** —— 100% 就说明太吵了 |
| `silenceDuringPlay` | **必须为 0** —— 玩家专注游戏时一次都不许插嘴 |
| `ignoredStreak` / `caution` | 被忽略后上升，被回应后回落 |

还有一个约束：**主动档位的上限由「实际读得到什么」决定**。
只读得到存档变更和进程退出的 adapter，无论用户怎么调都封顶在保守档 ——
因为调高档位却读不到新东西，只会逼桌宠编内容。

## 角色卡：规范格式 + 填表式生成

格式只在 [`core/card-spec.mjs`](core/card-spec.mjs) 里写**一次**，三样东西都从它派生：
校验规则、填表用的空表与提问、人读的文档 [`docs/CARD.md`](docs/CARD.md)
（**文档是生成的**，有一道测试盯着它与 spec 逐字一致 —— 手改文档会测试失败）。

每个字段都要回答四件事：**哪一层 · 谁有资格填 · 类型与取值范围 · 填错会怎样**。
其中「谁有资格填」是核心：

| fill | 含义 |
|---|---|
| `derived` | 程序派生（如 `id`），**模型与用户都不该填** |
| `user` | 只能由用户指定（`style` / `emojiPolicy` 这类主观选择） |
| `model` | 模型可以提议填入；标了「需出处」的还必须给 quote，且要能**逐字对上**原文 |

**不让模型即兴生成**，而是**先出表、再填**：空表的格子由 spec 定死，
模型只负责把值填进去 —— **未登记的格子直接被拒**。
实测一个"会编东西"的模型：它填了 8 格，2 格被挡下（自己加的 `favoriteColor` 未登记、
`mustMention` 不是给模型填的），剩下 6 格经**逐格确认**才写入。

**人物卡页第①段就是这条流程**：建草稿卡 → 抓取/粘贴原文 → 出表并填 → 勾选确认 → 写入。
Electron 自检会驱动界面走一遍（**30/30**，其中 6 条在验这条流程），并把过程截图存档。

```bash
node tools/gen-card-doc.mjs            # 从 spec 重新生成 docs/CARD.md
node tools/gen-card-doc.mjs --check    # 检查文档是否与 spec 一致
```

## 解码链在真实游戏上的成绩

拿本机 **50 个真实游戏目录、162 个存档候选**实测（`npm run probe` 可复现；
这是**本机当前状态**的快照 —— 装/卸游戏会变，所以别把百分比当常数）：

| 解码链首层 | 数量 | 完全解开 |
|---|---|---|
| `json` | 44 | **44** |
| `xml` | 13 | **13** |
| `base64` / `json@offset` / `godot-resource` / `ini` | 各 1 | **各 1** |
| `binary`（高熵） | 56 | 0 |
| `base64-binary`（加密/压缩包着二进制） | 24 | 0 |
| `dotnet-binaryformatter` | 17 | 0 |
| `text`（纯文本但不是结构化存档） | 4 | 0 |
| **合计** | **162** | **61 = 37.7%** |

两条实测教训：
- **扩展名会骗人**：`.dat` `.sav` `.data` `.mdrgslot` 里装的都是明文 JSON，所以解码链**按内容嗅探**。
- **Unity 的 `Player.log` 指望不上**：它一定存在，但内容基本是引擎噪声（单个最大 6.2MB），
  可靠能抽出来的只有"这一局开始了/结束了"。详见 `docs/ARCHITECTURE.md` §2。

> 那 62% 解不开的存档**不影响可用性**：仅凭"文件被写入"就足以驱动时机引擎
> （架构原则 P2 —— 局限是设计资源，不是缺陷）。

## capability 是「运行时事实」，不是引擎属性

同一个引擎的不同游戏能读到的东西可以完全不同。实测（`npm run inspect`）：

| 游戏 | 引擎 | 存档 | 解出 | 可读能力 | 生效档位 |
|---|---|---|---|---|---|
| 空洞骑士 | Unity | 6 个（.NET BinaryFormatter） | **0** | `exit、save` | **conservative（被封顶）** |
| すと～きんぐ！ | Unity | 4 个（明文 JSON） | **4** | `area、exit、item、progress、save` | **moderate** |
| 30 Days in the Workplace | Godot | 2 个（`.tres` 文本） | **2** | `area、exit、item、progress、save` | **moderate** |

所以 adapter 只声明「结构上总能拿到」的类型，运行中再按**实测证据**升级；
读不出内容的游戏会被自动封顶在保守档 —— 因为把档位调高却读不到新东西，只会逼桌宠编内容。

## 「度」是怎么保证的：长跑验证

时机引擎的价值全在**长时间下的度** —— 会不会越说越多、会不会在你正打的时候插嘴、
待发言队列会不会无限膨胀。这些单次快照看不出来，所以有一条专门的长跑验证：

```bash
npm run longrun                  # 模拟 6 小时（注入时钟，可复现）
npm run longrun -- --real 40     # 真实挂钟 40 秒（真的等，验证真实时钟路径）
```

**6 小时模拟实测（11/11 断言通过，跑完约 35 秒）**：

| 项 | 实测 |
|---|---|
| 事件 | 349 条（58.2/小时） |
| 主动开口 | 8 次，**全部落在「刚存完档往后一靠」/「中途休息」/「退出游戏」** |
| **玩家正在打时开口** | **0 次** |
| 开口时的最小空闲 | 10.0 秒 = 门槛（没有贴着边界说话） |
| 触发延迟 | p50 70s · max 148s —— 这就是"等松懈"的代价 |
| 没说的原因 | 还在专注继续等 6448 · 等太久作废 3 · 冷却中 20 |
| 状态体积 | 峰值 **23 KB**（没有泄漏） |

> ⚠ 诚实边界：长跑验证**注入时钟**，验的是引擎逻辑在长时间下的行为。
> `--real` 那一档才用真实挂钟（受时长限制，只能验路径通不通）。
> **仍未被验证**的一条：`relaxedIdleSec = 10s` 意味着"10 秒没碰键鼠"就算松懈，
> 而看剧情过场时几分钟不碰键鼠很常见 —— **有在过场里插嘴的风险**。

## 素材层：三种画风 + 两条质量闸门

「立绘 → 多风格多动作」最容易含糊带过的是质量。AI 生图有两个经典失败模式：
**偷懒**（六个动作给你六张几乎一样的图，桌宠还是傻站着）和**跑形**（每个动作一张新图，
前后不是同一个角色）。两者都能靠像素自动判定：

| 闸门 | 实测（程序化 provider） | 阈值 |
|---|---|---|
| 动作间最小平均像素差 | 0.032 | ≥ 0.01 |
| 与立绘的最大哈希距离 | 11 | ≤ 24 |

支撑它的是一个**零依赖的 PNG 编解码器**（`art/image.mjs`）—— 没有它，这两条只能停留在口头上。
阈值也是拿 `npm run art -- --measure` 实测之后才定的，不是拍脑袋。

**画风**（`card.animation.style`）也是真的生效，三种都可验证、也都用 read_image 看过：

| 风格 | 颜色数 | 高频(均值) | 边缘占比 | 性质 |
|---|---|---|---|---|
| 原图 | 4 | 1.36 / 0.92 | 0.115 / 0.086 | —— |
| `soft` 柔和 | **32** | **1.01 / 0.70** | 0.095 / 0.082 | 模糊造出中间色、高频最低 |
| `pixel` 像素 | **4** | 1.08 / 0.75 | 0.135 / 0.098 | **保留调色板** + 方块化 |
| `line` 线稿 | 5 | **11.6 / 7.5** | **0.222 / 0.163** | 只剩线，边缘占比最高 |

测试断言的是**方向**（"soft 颜色该变多""pixel 颜色不该增""line 边缘占比该最高"），
而不是弱得多的「输出不一样」—— 后者改一个像素就满足了。

> ⚠ 管线顺序是有讲究的：**风格化 → 动作**，而且质量闸门的**比较基准用风格化之后的立绘**。
> 反过来的话，线稿风会因"跟原图差太远"被判成跑形 —— 那是把**风格差异误判成跑形**。
